# v1.0.0 — One window for your agents and all their work

Until now, working with Vepol meant a handful of terminal tabs: one agent here,
another there, the task board only as a text file, the scheduled routines visible
only in logs. Vepol 1.0 gives all of that one home. A native Mac app runs your
agent in a real terminal inside the window, and around it you see every session,
every project's tasks and every scheduled routine with its state and history.

Underneath, Vepol now knows which of your agent CLIs can actually do work right
now, every agent session starts with the whole briefing instead of a slice of it,
and the planning rules got shorter.

1.0 is also a promise about the core. The knowledge folder layout, the
`kb-board` task board (its file format and its commands) and installing and
upgrading have run the maintainer's daily work for months. From this release on
they follow semantic versioning: an incompatible change to them comes only with
a new major version. Other `kb-*` commands and the background-process settings
in `processes.yaml` may still change within 1.x; every such change is called
out in the [changelog](../../CHANGELOG.md).

## What you get

- **Vepol Desktop.** A native macOS app: your agent in a real terminal inside
  the window, a session board, a Tasks view over every project's backlog, an
  Automations view over every scheduled routine, a read-only view of each
  project's knowledge, and a usage bar for your agent plans.
- **A live answer to "which agent can work right now?"** `kb-runtime-registry`
  asks each agent CLI a tiny question with a known answer and shows the result
  in one table: installed, logged in, within quota, answering.
- **Every session starts with the whole picture.** The startup briefing arrives
  complete, and it ends with a checksum line so an agent can prove it received
  all of it.
- **Publishing fails safe.** The seed-content audit never calls a seed clean when
  it could not check it.
- **Lighter planning.** One short, code-aware spec review, and specs capped at
  150 lines that answer four plain questions.

## Vepol Desktop

Vepol Desktop lives in [`face/`](../../face/README.md). It is a native macOS
window over a small local backend.

**Your agent, in a real terminal, inside the window.** Each project gets one
terminal per runtime (Claude Code or Codex). It is a full interactive terminal:
you type straight into it, it follows the window size, and the agent's own
interface works as it does in any terminal. A session never starts an agent on
its own: the agent starts only when you click, and opening a session only
attaches to it. Close the window or quit the app and the agent keeps running;
reopening re-attaches to the same process. The header and the board card show
the agent's state from process evidence: running with its PID, not running with
a Start button, or unknown with the reason. A composer below the terminal
pastes a longer prompt for you.

**Session board.** Five stages — Queue, Research, Working, Review, Done — that
you move cards between by drag and drop or a stage selector, with search and a
project filter. A «+» in any column creates a session directly in that stage.
Every card shows folder · project · path on disk, and a click anywhere on the
card opens it.

**Tasks.** Every project's `knowledge/backlog.md`, read through `kb-board`, in
one table with status chips and search. «Start session» opens that project's
terminal with the task text typed into the composer; nothing is sent until you
send it. The view never writes a board.

**Automations.** Every process in your `processes.yaml` with its schedule,
dependency, state and the reason for it, last and next run, a 14-day history and
the tail of its output — plus your Hermes cron jobs if you use Hermes, and the
`com.knowledge.backup` launchd job when it is loaded or installed. It is
read-only and built from the files the scheduler already writes; «Unknown» means
there is no evidence, never a guess.

**Session view and Knowledge.** A project → sessions tree on the left, and next
to each session a Knowledge tab: a read-only explorer of the project's
`knowledge/` folder with collapsible folders, a name filter across all of them,
and files opened as plain text.

**Usage at a glance.** A status bar shows how much of your Claude plan (5-hour
and 7-day windows) and your Codex plan you have used, with an «as of» time. It
reads only local files: no network call and no credentials.

**Local and private.** The backend listens on `127.0.0.1` only. The app hands
the page a per-launch token in memory; it never lands on disk or in a URL. The
whole interface is in English. Conversations you started in builds from `main`
before 1.0 keep their history and still open.

Build and open it from your Vepol checkout on an Apple Silicon Mac:

```sh
cd ~/vepol/face
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
./desktop/build.sh
open desktop/build/VepolDesktop.app
```

The app needs Python 3.11 or later (for example from `brew install python`);
create `.venv` with that interpreter. The terminal sessions need `tmux`
(`brew install tmux`). The build uses the Command Line Tools you already have.
See [`face/README.md`](../../face/README.md) for the usage-bar setup and the
test suites.

## Know which of your agents can work right now

You probably run several agent CLIs. Being installed is not the same as being
able to work: one is logged out, one has hit its usage cap, one answers with an
empty reply. `kb-runtime-registry` shows the truth per runtime, with eight
fields — `installed`, `authenticated`, `quota_available`, `healthy`,
`resumable`, `interactive`, `web_current`, `edit_capable` — each `yes`, `no` or
`unknown`.

- `kb-runtime-registry --report` (the default) renders the table and never
  spends quota.
- `kb-runtime-registry --probe [<runtime>…]` sends one trivial prompt with a
  known answer and records the result. Success means a clean exit **and** the
  expected answer in the output.
- `kb-runtime-registry --json` emits a document that validates against the
  schema shipped with the package, for your own tools.

A runtime counts as `available` only after a successful known-answer probe, or
a successful run through the orchestrator, in the last 24 hours with no active
cooldown. `unknown` is shown as degraded, never as
available. A probe refuses to run from inside an agent session, so a nested
check can never mark a healthy runtime as dead.

The roster now has seven runtimes: `claude`, `codex`, `agy`, `grok`,
`notebooklm`, `opencode` and `hermes` (Nous Research Hermes Agent).

## Every session starts with the whole picture

At the start of each session Vepol hands your agent a briefing: its role card,
the project's current state, the recent log, active tasks, open escalations and
the rules learned from past incidents. That briefing is now delivered whole:

- No per-section limits; the whole briefing fits a 250,000-character budget and
  is trimmed only above it — and then the briefing says exactly which part was
  trimmed.
- It opens with a short note on how to read the rest if a runtime shows only
  the beginning, and ends with a line like
  `KB-STARTUP-BUNDLE-END v1 chars=<N> sha256=<H>`, so a complete briefing can be
  told from a cut one by simple arithmetic.
- Each section reports what it actually contains — `present`, `clipped`,
  `omitted`, `empty` or `missing` — counted after the briefing is assembled.

## Publishing fails safe

If you publish your own seed from your knowledge base, `kb-doctor
seed-content-audit` checks that it carries only structure, never personal data.
The audit now first proves that the seed folder is its own git repository, lists
tracked files in a way that unusual file names cannot hide from, and ignores git
settings inherited from the calling shell. Anything that stops it from checking
becomes a blocking finding that names the cause: "could not check" is never
reported as "clean".

## Lighter planning

Vepol's development loop — the process your agents follow for non-trivial work —
is shorter and easier to act on:

- **One lightweight review.** One independent reviewer reads the spec and the
  relevant code once and answers `GO`, up to three questions, or a proven
  logical `BLOCK`. A new spec hash alone never triggers another review. Your
  approval, tests, evidence and write-back to the knowledge base stay.
- **Specs you can read in one sitting.** A spec is at most 150 lines and answers
  four questions under any headings: what we do, how it works (every branch
  named), what is out of scope, and how we check it. Review rounds, research and
  history live in the knowledge base and are linked, not pasted in.
- New projects created with `new-wiki` no longer switch on an automatic
  stop-time review.

## Fixed

- Resumed Codex conversations keep working past the first turn.
- The orchestrator's Claude lane waits for Claude to finish instead of cutting
  it off at a fixed timeout.
- The durable Claude launcher `kb-claude-run` now ships with the package, so the
  registry's Claude check and the orchestrator's Claude lane work on a fresh
  install.
- Running the shipped test suite (`tests/run-all.sh`) no longer sends prompts
  to your installed agent CLIs or adds runs to your own run history; only the
  install checks ask your `codex` for its version.

## Upgrading

From an existing install:

```sh
cd ~/vepol && ./upgrade.sh
```

`upgrade.sh` pulls the release, re-applies the installer (your data in
`~/knowledge` is never touched) and verifies the result. If you update with a
plain `git pull` instead, run `./install.sh --apply` afterwards; until then
`kb-doctor install-health` reports that the installed version and the checkout
differ.

- Your existing agent roster in `~/knowledge/.orchestrator/cli-tools.tsv` is
  kept as it is. If you use Hermes, copy the `hermes` line from
  `bin/cli-tools.tsv` into it.
- Run `kb-runtime-registry --probe` once from a normal shell to fill the
  registry; until a runtime has a fresh successful check, it is not shown as
  available.
- If you publish a seed folder that is not a git repository of its own, the seed
  audit now stops with a `no-git` finding. Make the seed its own repository.
- Vepol Desktop is optional and separate from the installer; build it when you
  want it (see above).

No data migration is needed.

## Known limits

- macOS 13 or later only.
- Vepol Desktop is built from source on your Mac (Apple Silicon, Command Line
  Tools, Python 3.11 or later). The build uses your Command Line Tools' SDK;
  pass `SDK=<path>` to `./desktop/build.sh` to use another. It is signed for
  local use only, not notarized, and it runs from your checkout and its
  `.venv`: move the checkout and you rebuild.
- The app uses port 8781. If something else holds it, the app says so and
  offers Retry.
- Tasks, Automations and Knowledge are read-only views.
- Claude Code is the runtime tried end to end in the in-app terminal; Codex in
  the terminal is covered by the automated journeys with a stand-in agent.
- Claude numbers in the usage bar need one line in your Claude Code status-line
  script (see [`face/README.md`](../../face/README.md)).
