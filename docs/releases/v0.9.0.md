# v0.9.0 — Vepol sees which of your agents is alive

You run several AI agent CLIs. Until now Vepol could only tell you which of
them were *installed*. It could not tell you which of them could actually do
work right now: one is logged out, one hit its usage cap for five days while
its retry cooldown expired an hour ago, one prints an empty answer with exit 0.
This release adds a registry that asks each agent and shows the truth in one
table. It also fixes a bug that killed every codex conversation from the
second turn.

## What you get

`kb-runtime-registry` reads the same CLI roster your agents already use
(`cli-tools.tsv`) and reports, per runtime, eight tri-state fields:
`installed`, `authenticated`, `quota_available`, `healthy`, `resumable`,
`interactive`, `web_current`, `edit_capable`. Every field is `yes`, `no`, or
`unknown` — and `unknown` renders as degraded, never as available.

```
$ kb-runtime-registry --report
| runtime | installed | authenticated | quota_available | healthy | ... | available | observed | evidence |
| claude  | yes | yes | yes | yes | ... | yes | 12s ago (probe) | probe claude rc=0 stdout_bytes=10: token CLAUDE_OK present |
| codex   | yes | yes | yes | yes | ... | yes | 7m ago (probe)  | probe codex rc=0 stdout_bytes=9: token CODEX_OK present |
| agy     | yes | unknown | unknown | unknown | ... | no | never | — |
```

Three modes:

- `--report` (default) renders the table and **never** spends quota.
- `--probe [<runtime>…]` sends one trivial prompt with a known token, records
  the result, then reports. Success means exit 0 **and** the token in stdout;
  exit 0 with empty output is recorded as a failure.
- `--json` emits a document that validates against the pinned schema shipped
  with the package, for other tools to consume.

The core rule: a runtime becomes `available` only on a **successful, fresh
observation** (within 24 hours) with no active cooldown. An elapsed cooldown, a
binary on `PATH`, or the absence of a recorded failure never count. Broker
observations from `kb-orchestrator-run` are read, never modified; the registry's
own cache (`.orchestrator/runtime-registry.json`) is a cache, not truth — delete
it any time and probe again.

A probe refuses to run inside an agent session (the agent-session environment
markers are detected) and exits 3 without recording anything, because a
nested probe yields anomalous results and could mark a healthy runtime dead.

Seven runtimes are in the roster now: `claude`, `codex`, `agy`, `grok`,
`notebooklm`, `opencode`, and `hermes` (Nous Research Hermes Agent, one-shot
`hermes -z`). `notebooklm` is an artifact CLI, not an agent, so it has no
probe and stays `unknown` on the observed fields.

## Fixed

- **Codex conversations died from turn 2.** `kb-orchestrator-run` built
  `codex exec resume <id> -C <cwd>`, and `codex exec resume` rejects `-C`, so
  every resumed codex session exited 1. The resume argv no longer carries `-C`.
- The claude lane of `kb-orchestrator-run` now runs through the durable
  runner and always waits for natural exit; there is no wall-clock timeout
  around Claude any more.
- `bin/kb-claude-run`, the durable Claude launcher that the claude probe and
  the claude lane exec, now ships with the tree; earlier trains shipped only
  its module (`_kb_claude_runner.py`) without the entry point.

## Upgrading

Pull the release. `install.sh` copies `bin/cli-tools.tsv` into
`~/knowledge/.orchestrator/` only when no roster exists there (`cp -n`), so an
existing install keeps its roster; add the `hermes` line by hand if you use
Hermes. No other configuration or data changes.

The shipped test suite tests its own tree: `tests/run-all.sh` is green end to
end from a clean checkout, including the new `runtime-registry` leg (hermetic,
no network, no quota). A separately invocable live smoke,
`tests/runtime-registry/live-smoke.sh <runtime>`, probes a real runtime from a
non-nested shell.
